# 档案人员编辑入口与服务事件分类设计

## 目标

1. 在“发布记录”的“职位与下级录入”区域中，取消所有人员姓名后的“编辑”按钮。
2. 在新增、编辑档案事件时，为事件分类增加“服务事件”，并确保 API 能保存该值。

## 范围

- 仅移除职位与下级录入卡片中紧随人员姓名显示的编辑入口。
- 保留点击职位或下级栏目进入事件录入的能力。
- 保留独立岗位资料管理页面和已有权限校验，不改变人员、岗位或档案记录的数据。
- “服务事件”加入共享前端分类集合与 API 云函数允许值，不改变既有分类的推断和历史数据。

## 实现

- 从 `pages/archive/create` 的模板中移除负责人及下级人员的编辑控件。
- 清理该页面仅为编辑控件服务的状态、事件处理函数、提示文案和样式，同时保持目录可见性仍由现有录入权限决定。
- 在 `miniprogram/utils/event-category.js` 的分类集合中加入“服务事件”，使新增/编辑选择器和档案筛选复用同一值。
- 在 `cloudfunctions/api/index.js` 的事件类型白名单中加入“服务事件”，防止保存时被归一化为其他分类。

## 权限与合规

- 分类为 `review-safe`：功能仍属于组织内部档案管理，不增加公开发布、互动或社交能力。
- 不降低云函数写权限，不新增个人信息，不修改数据库结构。
- API 云函数发生变更，测试前必须重新部署 `cloudfunctions/api`。

## 验证

- 回归测试证明人员姓名后不再出现编辑控件或跳转处理。
- 分类测试证明“服务事件”可供前端选择，并被 API 白名单接受。
- 执行全部 Node 测试、JavaScript 语法检查和 `git diff --check`。
