# 21纪事本：发布审核与长期架构硬约束

## 1. 文档地位

本文件是本项目所有需求、代码修改、云端配置和发布操作的前置约束。优先级高于普通功能需求。

任何变更开始前必须回答：

- 是否影响个人主体可选服务类目、主体认证或小程序备案？
- 是否可能被认定为社交、论坛、社区、公开信息发布或开放式用户生成内容？
- 是否扩大个人信息收集、公开展示或跨组织访问？
- 是否破坏云端权限校验、操作日志或服务队数据隔离？
- 是否把 CloudBase 专有实现泄漏到页面层，增加未来迁移成本？

无法确认时，先暂停发布并核对微信公众平台当前规则，不得用历史经验代替最新规则。

### 1.1 永久审核门禁

微信小程序过审是每一项未来开发任务的验收条件。需求分析、代码实现和发布前都必须执行审核检查，不能等到提审时再补救。

每次变更开始前必须留下审核影响结论：

- `审核安全`：符合个人主体当前类目、内部工具定位和最小权限原则；
- `有风险但已缓解`：说明风险、限制范围、前后端控制和验证证据；
- `阻塞`：缺少驳回原文、平台规则或主体资质信息，暂停实现或发布。

以下能力默认按高风险处理：多人提交文字或图片、公开公告和信息流、用户互动、报名收款、募捐筹款、支付交易、医疗健康信息、金融账目服务、敏感个人信息。

不得制作仅供审核的假界面、审核开关或“审核时隐藏、通过后开放”的双重能力。送审版本、云函数鉴权和上线后的实际行为必须保持一致。

微信审核驳回后，必须先将平台原文和截图信息登记到 `docs/review-rejection-log.md`，再进行定向整改。没有驳回原文时只能进行通用降风险处理，不能宣称问题已经修复或保证通过。

## 2. 发布与审核第一原则

项目定位固定为：**组织内部的岗位、档案、待办、通讯录和历史纪事管理工具**。

默认禁止新增：

- 用户公开发帖、公开图文分享、评论、点赞、关注、粉丝、排行榜社交互动；
- 论坛、开放聊天室、陌生人互动、公开征集内容；
- 用户自行生成并向不特定用户传播文字、图片、音频或视频；
- 容易被理解为官方机构认证、政府身份认证或微信实名认证的功能文案；
- 与个人主体当前可选类目不一致的经营、交易、募捐、医疗、金融等能力。

档案内容应由授权岗位人员在明确组织范围内录入，仅服务内部管理。发布前应保留审核说明截图，证明系统没有公开社交和开放式 UGC。

## 3. 个人主体、备案与认证

- AppID、主体、服务类目、备案状态和隐私保护指引必须在每次提交审核前复核。
- “内部身份资料”只用于识别成员及分配权限，不得称为“实名认证”。
- 默认只收集姓名、所属组织和系统账号编号。手机号、身份证、证件照片、人脸信息默认不收集。
- 如未来确需敏感信息，必须先完成必要性说明、隐私政策更新、数据权限设计和微信平台合规核对。
- 不能承诺审核一定通过；只能通过减少风险、保持类目与实际功能一致来提高通过概率。

官方核对入口：

- [微信公众平台](https://mp.weixin.qq.com/)：主体信息、服务类目、小程序备案、版本审核和驳回详情。
- [微信开放文档](https://developers.weixin.qq.com/miniprogram/product/)：小程序产品、运营与接口要求。
- 微信公众平台后台的“设置 → 基本设置/服务类目/小程序备案/用户隐私保护指引”以提交当日界面为准。

## 4. 身份和权限架构

权限必须由四个维度共同决定：

1. 人员：`userId`；
2. 组织：协作区或具体服务队；
3. 资源：档案、通讯录、待办、历史事件、通知、照片等；
4. 范围与任期：单岗位、岗位树、当前组织、组织树、开始日期和结束日期。

角色：

- `super_admin`：全系统管理；
- `area_admin`：协作区及下级组织；
- `team_admin`：指定服务队；
- `role_manager`：有效任期内的岗位负责人；
- `member`：普通内部成员。

精细授权存储在 `permission_grant`，多条权限按并集生效。授权至少包含：

- `userId`
- `organizationId`
- `module`
- `scopeType`
- `scopeId`
- `actions`
- `startDate`
- `endDate`
- `status`

所有新增、修改、删除、审核和授权必须由云函数再次校验，并写入 `operation_log`。页面隐藏按钮不能代替服务端权限。

## 5. 数据隔离

- 协作区数据与各服务队数据具有明确 `organizationId`。
- 服务队管理员不能读取或修改其他服务队的受限数据。
- 岗位负责人只能维护有效任期及授权范围内的数据。
- 司库账目允许成员查看，但新增、修改和删除仅管理员、当前司库或明确授权人员执行。
- 删除优先采用状态和 `deletedAt` 软删除，避免不可恢复的数据损失。

## 6. 代码边界

- 页面统一调用 `utils/api.js`。
- 角色、菜单和资源权限统一由 `utils/permission.js` 表达。
- 组织读取经过 `organizationService`。
- 纪事、图片和账目经过 `eventService`。
- 用户、角色和授权经过 `userService`。
- 页面层禁止出现 `wx.cloud.database()`、集合名称或 CloudBase 数据结构。
- CloudBase 调用只能位于 service/provider 或云函数层。

### 6.1 深色表单输入规范

所有深色背景表单必须避免“输入了但看不见字”的问题：

- `input` 和 `textarea` 必须显式设置文字色、占位色和光标色；
- 深色表单建议使用 `placeholder-class`，不要只依赖默认占位样式；
- 关键输入框应设置稳定的同层渲染属性，避免基础库或真机暗色模式覆盖文字颜色；
- 样式中同时设置 `color` 和 `-webkit-text-fill-color`，确保 iOS、开发者工具和微信基础库表现一致；
- 新增表单页面发布前必须在开发者工具和真机预览中至少输入一次，确认文字、光标和占位文字都可见。

## 7. 未来迁移阿里云

当前使用微信云开发，但数据结构和接口必须能迁移到：

- 独立服务器；
- 阿里云 RDS MySQL；
- 阿里云 OSS。

迁移约束：

- 业务主键使用独立 `id`，不把 CloudBase `_id` 当作跨平台唯一业务键；
- 图片保存在 `event_image`，纪事主表不内嵌图片数据；
- 所有业务图片和文件必须通过统一的 `uploadOrgFile(params)` 上传，按组织、服务队、岗位端口和事件名称归档，并在 `file_records` 保存云路径、文件标识和上传人；
- 图片同时保存 `provider`、`fileId/imageUrl` 和可迁移的 `objectKey`；
- 时间、状态、组织和操作人字段保持明确；
- 页面只依赖统一 API 返回模型，不依赖 CloudBase 查询语法；
- 新集合设计时同步给出未来 MySQL 表、索引和外键映射思路。

## 8. 每次发布前检查清单

- [ ] 服务类目与当前实际功能一致；
- [ ] 主体认证、备案和隐私保护指引状态已核对；
- [ ] 没有 AI 助手、公开社交、评论、论坛或开放式 UGC 入口；
- [ ] 测试账号能进入审核所需页面，不出现空白页和超时；
- [ ] 普通成员无法看到新增、编辑、删除按钮；
- [ ] 云函数对越权请求返回拒绝；
- [ ] 服务队之间数据隔离通过测试；
- [ ] 个人信息收集保持最小化；
- [ ] 云函数、数据库集合和索引已部署；
- [ ] 如本次修改涉及 `cloudfunctions/`，已明确提醒并重新部署对应云函数；
- [ ] 操作日志正常；
- [ ] 主包体积、图片大小和隐私接口通过开发者工具检查；
- [ ] 本次版本的审核说明写清“内部组织管理工具，不提供用户公开发布和社交互动”。
- [ ] 本次新增功能已有明确的审核影响结论，且与实际上线行为一致；
- [ ] 如上次审核被驳回，已在 `docs/review-rejection-log.md` 登记原文、整改和验证证据；
